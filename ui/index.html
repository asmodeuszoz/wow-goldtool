Item card

the item card is a WINDOW, not a tab: clicking a Search row’s `card` button opens it OVER the tab you are on (its item id fills the window’s field and `Read the DB` answers with ZERO requests), and the window floats until `Close this window` closes it - the tab underneath stays where it was, and typing another item id into the field plus pressing `Read the DB` reads the SAME door again. the card reads the DB: it answers offline, prices are shown as the game’s money with the exact copper in each hover, the live min buyout row reads "no price" until the price refresh ran - the Sync tab’s Price button or the CLI stage, one live ask per copied record ever, and the door can also answer that the AH offers nothing right now - and on the card itself "Re-check online" is the only button that touches the API

Recipe card — one entry, as the game shows it

the recipe card is a WINDOW, not a tab: clicking a Recipes row’s recipe name opens it OVER the Recipes tab (the row’s spell id fills the window’s field and its door is read), `Close this window` closes it, and the tab underneath stays where it was. the card reads the DB: ZERO requests leave this door. The entry’s job, name and skill words are the fetched set’s own; every cell answers through the item rows this DB owns, BY VALUE on the ids the set states - the scroll that teaches this recipe is named by the set’s OWN learned-from bytes, the crafted item and the materials by their ids. A gap keeps its own state word: the set may name no scroll at all, name one this DB never saw, state nothing about how the recipe is learned, or name no crafted item at all (the set’s enchanting entries). A cell shows the game’s money beside every copper number and the record’s OWN copied tooltip where the tooltip stage copied one

The DB's own writes

the user's own writes: these four buttons send NO request, and the values they write survive every later crawl write (ADR 0010) - an id here is one the DB has, an item the user makes lands in the reserved id block, and hiding is a tombstone (the row keeps its bytes so bringing it back restores everything)

Copies: reword the twins (sends no request)

ADR 0013's refresh: every copy the DB already holds gets its twin re-derived from the copy ITSELF — ZERO requests leave here, so this button asks the API nothing. It fixes the shape the v0.9.0 derivation left (glued words: `Worn ShortswordItem Level 2Main Hand...`) on DBs whose copies predate the corrected span rule, gives a copy whose twin was never born (a DB that copied at v0.8.x) its twin at birth, and re-running it answers 0 rewritten and changes nothing. The card's words row and the description search both read what it wrote.
